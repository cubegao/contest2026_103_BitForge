# ADR-0005：构建、镜像与烧录流程

- 状态：已采纳
- 日期：2026-09-06

## 1. 背景与目标

固件要在真机上跑起来，需要一条可重复的"配置 → 编译 → 镜像 → 烧录 → 终端"流水线。ESP32-P4 与既有的 C3/C6 构建流程有布局差异，需要固化为本项目的标准流程。

## 2. 流程定义

### 2.1 编译

```bash
./build_esp32p4.sh
# 等价于：
#   export ESP_HAL_3RDPARTY_URL=<fork 地址>
#   export ESP_HAL_3RDPARTY_VERSION=<完整 SHA>
#   ./build.sh vendor/espressif/boards/esp32p4/esp32p4-function-ev-board/configs/nsh --cmake -j$(nproc)
```

脚本同时注入代理变量与 HAL 版本 pin，保证远程依赖可复现。

### 2.2 镜像生成

构建结束时 CMake target 自动调用 esptool：

```bash
esptool --chip esp32p4 elf2image -fs 16MB -fm dio -ff 80m --ram-only-header -o nuttx.bin nuttx
```

关键约束（缺失任一条 ROM 将无法加载，表现为反复复位或静默挂死）：

- **`--ram-only-header` 不可省略**：P4 的 ROM 直接加载 RAM 段镜像，隐藏 ROM 段、不追加 SHA256 摘要；
- **flash 尺寸/模式/频率**：16MB / DIO / 80MHz，与板上 flash 一致。

### 2.3 烧录

```bash
esptool -c esp32p4 -p /dev/ttyACM0 -b 921600 \
    --before default-reset --after hard-reset write-flash 0x2000 nuttx.bin
```

- **写入偏移 0x2000**：ESP32-P4 的 ROM 从 0x2000 取镜像（区别于 C3/C6/H2 的 0x0，对应 tools/espressif/Config.mk 中 `BL_OFFSET := 0x2000`）；
- 烧录与终端共用同一 USB 口（见 ADR 的控制台决策，docs/adr/ADR-0004.md 的 defconfig）。

### 2.4 终端验证

- USB-Serial-JTAG 要求主机拉高 DTR，`cat /dev/ttyACM0` 无效，使用 minicom 或显式设置 DTR 的脚本；
- 复位会触发 USB 重枚举，串口工具需要支持断线重连（见 docs/issues/ISSUE-004）；
- 验证命令序列：`uname -a` → `ps` → `mount -t procfs /proc` → `free` → `dmesg`（ramlog 转储）。

## 3. 关键决策

- **构建脚本入仓**（`build_esp32p4.sh` 放在专属仓根目录），工作区根目录仅放软链——评委 clone 专属仓即可复现；
- **全量重建作为纪律**：defconfig、HAL 头文件、链接脚本任何变更后必须 `rm -rf cmake_out/<板>_<配置>/`（增量构建不会重新生成 `.config`，见 docs/issues/ISSUE-003）；
- **链接警告当错误对待**：`contains output sections; did you forget -T?` 这类警告曾是静默挂死的唯一线索（见 docs/issues/ISSUE-001）。

## 4. 验证方式

- 干净工作区从零到 `nsh>`：构建 1 分 20 秒左右，烧录 2 秒（900kbit/s），全程单线；
- 产物体积参考：最小 NSH 固件 `nuttx.bin` 约 231KB（含显示后约 248KB）。
