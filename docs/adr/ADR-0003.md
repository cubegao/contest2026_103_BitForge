# ADR-0003：esp-hal-3rdparty 依赖接入与适配

- 状态：已采纳
- 日期：2026-09-06

## 1. 背景与目标

NuttX 的 ESP 系芯片把寄存器头文件、HAL 组件与时钟/电源控制委托给外部仓库 esp-hal-3rdparty，构建系统在配置期自动拉取。P4 的启动流程与 NuttX 内存模型和 HAL 的默认假设存在出入，需要：依赖版本可复现地固定 + HAL 侧最小适配。

## 2. 适配流程

1. **确定基线**：以官方 release 基线（commit `b90b183`）为底，在自有 fork 的分支 `feat/openvela-esp32p4` 上工作；
2. **实施 P4 适配**（单个 commit，逐项可追溯）：
   - `esp_gpio_reserve.c`：去除新 GCC 不再接受的 `ATOMIC_VAR_INIT` 原子初始化写法；
   - `components/esp_hw_support/port/esp32p4/cpu_region_protect.c`：
     - NuttX 在 `esp_psram_init()` **之前**执行 PMP 区域保护，此时 PSRAM 堆大小还是 0，零长度 TOR 条目会导致整个 EXTRAM 窗口不可访问 → 回退为用 NAPOT 条目按 RW 开放完整 EXTRAM（cached + non-cached 两个别名区）；
     - LP 内存区间结束地址从 `SOC_RTC_IRAM_HIGH` 延伸到 `SOC_LP_PERIPH_HIGH`，覆盖 PMU/LDO 寄存器，否则 PSRAM/显示上电时访问该区间触发 Access Fault；
   - `components/esp_psram/device/esp_psram_impl_ap_hex.c`：MPLL LDO 上电稳定等待、PLL 锁定等待、PSRAM 连接探测重试（此阶段无定时器驱动，全部用忙等）；
   - `nuttx/esp32p4/include/sdkconfig.h`：`CONFIG_SPIRAM` 家族无条件定义（HAL 内部时钟门控只认它自己）、`CONFIG_SPIRAM_SPEED` 兜底默认值、关闭与 NuttX 内存布局冲突的 bootloader region protection 与 system memprot；
   - `nuttx/src/platform/os.c` / `os.h`：任务创建始终传完整 `posix_spawnattr_t`（空指针会崩溃），`usleep` 映射到 `nxsig_usleep`；
3. **版本固定（双重 pin）**：
   - CMake 路径：构建脚本导出 `ESP_HAL_3RDPARTY_URL`（fork 地址）+ `ESP_HAL_3RDPARTY_VERSION`（完整 40 位 SHA，当前 `a498192b2c15ad11c048a317c51d04389057bc74`）；
   - Make 路径：vendor 层 `scripts/Make.defs` 内设置同名变量（构建系统的 `ifndef` 机制允许外部覆盖）；
4. **注释规范**：HAL 修改中的注释全部重写为英文自有表述。

## 3. 关键决策

- **修复收编为自有提交**，不改动公共版本，不使用浮动分支名；
- **禁用 HAL 侧内存保护**（bootloader region protection、system memprot PMP）：这些保护面向 ESP-IDF 启动流程设计，与 NuttX 的自有 PMP 管理冲突；
- **本地离线兜底**：开发期可用 `configure.sh -S` 的 nxtmpdir 缓存机制绕过网络拉取，正式流程必须走版本 pin。

## 4. 验证方式

- 首次构建日志出现 `Cloning Espressif HAL for 3rd Party Platforms` 并检出指定 SHA；
- 真机 `free` 显示 34,004,200 字节总堆（768KB SRAM + 32MB PSRAM），开机 PSRAM 自检通过——证明 PSRAM 初始化与 PMP 适配生效；
- 显示链路的 PHY LDO 上电正常（PMU 寄存器可访问），证明 LP 区间扩展生效。

## 5. 产物

esp-hal-3rdparty 分支 `feat/openvela-esp32p4` commit：`fix(esp32p4): adapt P4 HAL paths to the NuttX boot flow`。
