# ISSUE-005：触摸样本数据链路——确认帧与轮询架构

- 日期：2026-09-12
- 状态：已解决
- 影响阶段：M6 触摸适配

## 1. 问题描述

GT911 触摸控制器（I2C0，0x5D）的 I2C 读写已通（产品 ID "911" 可读），
但 `/dev/input0` 的样本长期为空（npoints=0），触摸屏幕无任何事件上报。
调试过程中还多次出现"所有 I2C 写被拒、读正常"的卡死状态，只能断电恢复。

## 2. 排查过程与三个根因

### 根因一：确认帧（ack）缺失导致帧堵塞

GT911 每次触摸/释放会锁存一帧数据并置位 0x814E 的 bit7；**主机必须写 0
清除，否则控制器不再上报任何新帧**。早期实现只在"点数 ≥1"时才确认，
导致一个"bit7=1 但 0 点"的帧（抬起事件）永久堵塞后续所有触摸。

修复：**bit7=1 的帧无条件确认**（无论点数），与厂商驱动一致。

### 根因二：确认写的事务形态与重试策略

- 本 I2C 主控**拒绝 3 字节数据写**（指针+值）——用总线上的 ES8311 做
  对照实验确认（2 字节写成功、3 字节写 NACK），与 GT911 无关。
- 对确认写做背靠背重试会把控制器打入"所有写被拒、读正常"的卡死状态
  （三个独立实现均观察到，只能断电恢复）。

修复：确认帧采用 **4 字节单事务**（指针 0x814E + 状态清零 + track 字节
清零），**每帧至多尝试一次**，失败则下个 20ms 轮询周期自然重试。

### 根因三：I2C 流量与轮询架构

应用按需读取时，总线长时间静默；且应用 read() 里的 I2C 与轮询相互
竞争。重构为：**20ms 周期的 HPWORK 轮询工作项独占所有 I2C 流量**
（读状态 → 解码 → 确认 → 发布缓存样本 + poll 通知），应用 read() 只
拷贝缓存样本、零阻塞。

## 3. 附带发现与修复

- **驱动缺少 TSIOC_GETMAXPOINTS ioctl**：输入框架打开 /dev/input0 时
  必须获取最大触点数分配样本缓冲；ioctl 缺失导致 LVGL 输入设备创建
  直接失败（"get touch maxpoints failed"）。已实现（返回 1）。
- **esp_i2c.c 缺 spinlock.h**：`esp_i2c_reset`（CONFIG_I2C_RESET 路径）
  引用 `enter_critical_section` 但未包含 `nuttx/spinlock.h`，链接失败。
- **Kconfig 子选项被静默丢弃**：`DEBUG_INPUT_INFO` 等挂在
  `if DEBUG_INPUT` 块内，defconfig 只写子选项不写总开关会被忽略。

## 4. 最终验证

NSH 下后台 `hexdump /dev/input0 &`，手指触摸时样本变为有效帧：

```
0000: 01 00 00 00 00 19 6d 01 b0 00 00 00
      npoints=1  flags=0x19(DOWN|ID|POS)  x=365  y=432
```

坐标随触点实时变化，松手恢复 npoints=0，无 NACK 卡死复发。

## 5. 预防

- 触摸确认写**永不重试**（每帧一次），是防止控制器卡死的硬约束
- 面板类外设调试先跑 `hexdump` 看原始样本流，再接上层框架
- Kconfig 子选项必须确认总开关同时打开（对照 .config 而非 defconfig）
